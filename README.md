# Scalable URL Shortener Microservice

**Java 21 · MongoDB · PostgreSQL · Redis · Docker · AWS · k6**

A URL shortener built to be measured. It has two storage backends (MongoDB and PostgreSQL) behind one interface, chosen by configuration. It adds Redis caching with stampede protection, a distributed token-bucket rate limiter, API-key auth, and a k6 benchmark that compares the four storage/cache configurations under the same workload.

## Architecture

```
                 ┌──────────────────────────────────────────────┐
  client ──────▶ │  Spring Boot 4 app (Java 21, virtual threads) │
                 │                                              │
  POST /api/links│  ApiKeyFilter → RateLimitFilter (Redis Lua)  │
  DELETE /api/...│  LinkService                                 │
  GET  /{code}   │   ├─ CachedLinkResolver ──▶ Redis (cache)    │
                 │   │    cache-aside · negative cache ·        │
                 │   │    request coalescing · fail-over to DB  │
                 │   └─ LinkRepository (interface)              │
                 │        ├─ MongoLinkRepository ──▶ MongoDB    │
                 │        └─ PostgresLinkRepository ─▶ Postgres │
                 └──────────────────────────────────────────────┘
                 STORAGE=mongo|postgres       CACHE=true|false
```

The app is **stateless**: links live in the database, and the cache and rate-limit buckets live in Redis. N copies can run behind a load balancer, and the rate limit stays correct because it's enforced in Redis, not in app memory.

## API

| Method | Path | Auth | Body / response |
|---|---|---|---|
| POST | `/api/links` | `X-API-Key` | `{"url": "https://…", "ttlSeconds": 86400?}` → `201 {"code","shortUrl","url","expiresAt"}` |
| GET | `/{code}` | none | `302 Location: <url>`; `404` if unknown or expired |
| DELETE | `/api/links/{code}` | `X-API-Key` (owner) | `204`, or `404` |
| GET | `/actuator/health` | none | app, storage backend and Redis health |
| GET | `/actuator/prometheus` | none (blocked publicly by Caddy) | metrics |
| POST | `/admin/keys` | `X-Admin-Token` | `{"name"}` → `201 {"keyId","apiKey","name"}` (the key is shown once) |
| POST | `/admin/seed?count=100000` | `X-Admin-Token` | bulk-inserts load-test links and returns their codes |

Link creation is rate-limited per API key, and every response carries `X-RateLimit-Limit` and `X-RateLimit-Remaining`. A `429` response also includes `Retry-After`.

## Design decisions

### Random base62 codes (not a counter, not a hash)
Codes are 7 characters from `SecureRandom` over `[0-9A-Za-z]`, which gives 62⁷ ≈ 3.5 trillion possible codes. With 1 million links, a new code collides with probability ≈ 3×10⁻⁷. On a collision the service retries up to 3 times.
- **Uniqueness is enforced by the database's unique key** (`_id` in MongoDB, the `PRIMARY KEY` in Postgres), using insert-if-absent (`insertOne` and catching the duplicate-key error, or `ON CONFLICT DO NOTHING`). A select-then-insert check would race when two requests generate the same code.
- v1 used a Postgres sequence with base62 encoding. That made codes **enumerable** (anyone could walk every link), needed a central counter, and doesn't exist in MongoDB. Random codes need no coordination across instances or shards.

### 302, not 301
Browsers cache a 301, so later clicks never reach the service. Expiry and deletion would then stop working. A 302 keeps every click visible, at the cost of more traffic, which is why the cache matters.

### MongoDB: `_id` = short code, plus a TTL index
```js
{ _id: "aB3xK9q", url: "...", createdAt: ISODate, expiresAt: ISODate /* absent = permanent */, owner: "k_..." }
db.links.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0, name: "ttl_expiresAt" })
db.api_keys.createIndex({ name: 1 }, { unique: true })
```
- `_id`'s built-in unique index enforces code uniqueness and serves the redirect lookup, so no second index is needed.
- `expireAfterSeconds: 0` means each document expires at its own `expiresAt`. MongoDB's TTL monitor runs about every 60 s, so the **read path also filters on `expiresAt > now`**. Correctness never depends on cleanup timing.

### PostgreSQL: primary key, partial index and a cleanup job
Postgres has no TTL. A scheduled job deletes expired rows **in batches of 1,000** every minute, so it never holds long locks or causes WAL spikes. A partial index on `expires_at` covers only rows that can expire. The read path filters on expiry, exactly as in MongoDB.

### One interface, two backends, one contract test suite
`LinkRepository` is implemented by `MongoLinkRepository` and `PostgresLinkRepository`. `LinkRepositoryContract` holds the tests once and runs them against **both** backends using real databases in Testcontainers. Because both behave identically, the benchmark compares databases rather than different behaviour.

### Caching (Redis, cache-aside)
- **Cache-aside**: look in Redis first; on a miss, read the database and fill the cache. Keys look like `l:<code>`.
- **Cache TTL ≤ the link's remaining lifetime** (capped at 24 h), so an expired link is never served from cache.
- **Negative caching**: unknown codes are cached as `__404__` for 60 s, so bots and typos don't hit the database each time.
- **Stampede protection**: when a popular link's cache entry expires, many requests miss at once. Concurrent misses for the same code share one database load (`ConcurrentHashMap<String, CompletableFuture>`); the waiting virtual threads simply park. Across N instances that's at most N loads instead of thousands. Cross-instance alternatives would be a short Redis lock or probabilistic early refresh.
- **Graceful degradation**: Redis calls time out after 50 ms. On an error the service reads the database directly and skips Redis for 1 s. Redirects get slower but keep working.
- Redis runs with `maxmemory 256mb` and `allkeys-lru`, and persistence is off, because the cache can be rebuilt from the database.
- `CACHE=false` turns caching off completely (including coalescing), which gives the uncached baseline.

### Token-bucket rate limiting in Redis Lua
Each API key gets a bucket with capacity 20 and a refill rate of 5 tokens/s. Bursts of up to 20 are allowed, with a steady average of 5/s.
- The state is **shared in Redis**. An in-memory limiter would let N instances allow N times the limit.
- The read → refill → take → write sequence runs as **one Lua script, so it's atomic**. Two requests can't both see "1 token left". A test fires 100 concurrent requests at one bucket and checks that only about 20 get through.
- The script uses **the Redis server clock (`TIME`)**, so app instances with slightly different clocks refill consistently.
- `PEXPIRE` removes idle buckets automatically.
- The limiter **fails open** when Redis is down: briefly allowing extra link creation is better than blocking all of it. A payment system would fail closed instead.

### API keys
A key has the form `<keyId>.<secret>`, where the secret is 32 random bytes. Only **SHA-256(secret)** is stored, so a database leak doesn't expose usable keys. A fast hash is fine for long random secrets; passwords would need bcrypt or Argon2. Keys are compared in constant time (`MessageDigest.isEqual`), and lookups are cached in memory for 60 s.

### URL validation
Only `http` and `https` URLs with a host are accepted, up to 2,048 characters. URLs pointing back at this service are rejected (they would create redirect loops). `javascript:`, `data:` and `file:` URLs are rejected. Production shorteners also check URLs against phishing lists such as Safe Browsing.

### Virtual threads
`spring.threads.virtual.enabled=true` runs every request on a virtual thread, so blocking driver calls (the MongoDB sync driver and JDBC) are cheap to wait on. They don't make the database faster: the **connection pool becomes the concurrency limit** (Mongo `maxPoolSize` 100, Hikari 100). Hot paths use `ConcurrentHashMap` and `CompletableFuture`, not `synchronized`, to avoid pinning virtual threads on Java 21. To test the platform-thread baseline, set `VIRTUAL_THREADS=false`.

## Sharding plan (MongoDB)

**Links: shard on `{ _id: "hashed" }`.**

| Shard key | Distribution | Redirect query `{_id: code}` | Verdict |
|---|---|---|---|
| `{_id: "hashed"}` | Even: random codes hash uniformly | **Targeted** (one shard) | **Chosen** |
| `{_id: 1}` (ranged) | Random codes spread well, but chunks need splitting and balancing | Targeted | Acceptable; hashed is more predictable |
| `{createdAt: 1}` | **Monotonic**: every insert goes to the last chunk, creating one hot shard | Scatter-gather | Bad |
| `{owner: 1}` | Skewed: one big customer creates a jumbo chunk | Scatter-gather | Bad |

```js
sh.enableSharding("urlshortener")
sh.shardCollection("urlshortener.links", { _id: "hashed" })
```
Redirects make up almost all of the traffic and always include `_id`, so each one goes to a single shard. Writes spread evenly because the codes are random, and the TTL index works on sharded collections. Random codes also need no central counter, so there's nothing to coordinate across shards.

**Redis at scale:** Redis Cluster spreads `l:<code>` keys across hash slots. For one viral link (a hot key), a small in-process cache (Caffeine, 1–5 s TTL) in front of Redis absorbs the load.

**Click analytics (next step):** a time-series collection sharded on `{code: "hashed"}`, fed through Kafka for durability.

## Running locally

```bash
docker compose up -d --build                     # app (Postgres backend, cache on) + Redis + Postgres + MongoDB
STORAGE=mongo docker compose up -d app           # switch backend
# If port 27017 is already in use on your machine: MONGO_HOST_PORT=27018 docker compose up -d

# create an API key (ADMIN_TOKEN defaults to change-me-admin-token in compose)
curl -s -X POST localhost:8080/admin/keys -H 'X-Admin-Token: change-me-admin-token' \
     -H 'Content-Type: application/json' -d '{"name":"me"}'
curl -s -X POST localhost:8080/api/links -H 'X-API-Key: <apiKey>' \
     -H 'Content-Type: application/json' -d '{"url":"https://example.com","ttlSeconds":3600}'
curl -sI localhost:8080/<code>
```

Tests (Docker required; Testcontainers starts MongoDB, PostgreSQL and Redis):
```bash
./mvnw verify
```

```bash
./loadtest/run_matrix.sh                     # full: 4 configs × 5 rates × 3 repeats, 60 s each (~1h45m)
```

Before running, stop other heavy containers and apps; they compete for CPU with the system under test. Raw k6 summaries are written to `results/raw/`, and the tables to `results/results.md`.

**Redis-down experiment:** while a cached run is in progress, run `docker compose stop redis`. Latency rises to uncached levels, but the error rate stays near zero.

## v1 → v2

| | v1 | v2 |
|---|---|---|
| Storage | PostgreSQL via JPA | `LinkRepository` with MongoDB **and** PostgreSQL implementations, chosen by config |
| Codes | Postgres sequence + base62 (enumerable) | Random base62 from `SecureRandom`; database unique key + retry |
| Expiry | none | MongoDB TTL index / Postgres batched cleanup, both checked on read |
| Cache | Basic cache-aside | + negative cache, TTL ≤ expiry, request coalescing, fallback when Redis is down |
| Rate limit | Leaky bucket per IP; Lua `HSET` call was malformed, so every request errored | Token bucket per API key, atomic Lua, rate-limit headers, fails open |
| Auth | none | API keys stored as SHA-256 hashes, compared in constant time |
| Tests | `contextLoads` only | 53 tests: contract tests on both databases, limiter, coalescing, end to end |
| Ops | compose with databases only | Multi-stage Dockerfile, CI, AWS deploy with HTTPS, Prometheus metrics |
| Performance | unmeasured ("O(1) caching") | k6 matrix with percentiles and hit rate |

## Limitations and next steps
- **Click analytics**: an async batched recorder feeding a MongoDB time-series collection, plus a `$dateTrunc` aggregation for daily stats. Use Kafka for durable click events.
- Coalescing happens per instance. Cross-instance coalescing would need a Redis lock.
- Multi-region deployment, and edge or CDN redirects for the hottest links.
